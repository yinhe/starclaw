### 1.2 缺失模块（尚未开发）

| 缺失项 | 影响 | 阻塞的商业能力 |
|--------|------|---------------|
| Overlord 终端用户界面（`web/`） | 企业员工无法使用 AI | ❌ Overlord 不可卖 |
| Overlord 计费/SSO/审计增强 | 无法满足 Pro 以上需求 | ❌ 高价值客户无法签 |
| Router 完整计费流 | 星能消耗无法收费 | ❌ 用量收入为零 |
| 官网落地页（`queen/site/`） | 陌生客户找不到产品 | ❌ 开源获客无入口 |
| Queen City Portal | 城市合伙人无后台 | ❌ 渠道无法招募 |
| Queen Partner Hub | 核心合伙人无 CRM | ❌ 内部管理靠微信 |
| Overlord 白牌引擎 + 许可证 | 功能分级未生效 | ❌ 白牌客户无法卖 |
| Queen 结算引擎 | 佣金手工计算 | ❌ 10+ 合伙人时崩溃 |
| 移动端（`queen/mobile/`） | 无移动端入口 | ⚠️ 影响使用场景 |
| Overlord SDK | 无法嵌入客户系统 | ⚠️ 限制集成场景 |
| P2P 高级组网 | 无分布式壁垒 | ⚠️ 长期竞争力 |

### 1.3 战略判断

```
虫后三条军规：
  1. 先能卖 → 再能管 → 再能放大
  2. 每一步交付必须「解锁收入」或「解锁增长」
  3. 一个人干的阶段，只做能独立交付的模块

核心洞察：
  小龙虾最稀缺的不是技术能力（Claw Phase 1-5 已经很强），
  而是把技术变成可卖的企业产品（Overlord 三件套）。
  
依赖链：
  收入 = Overlord 订阅 + 星能消耗
  Overlord 可卖 = 终端用户能用（web）+ 企业管控（billing/SSO）
  渠道放大 = 合伙人有工具（City Portal / Partner Hub）
  品牌溢价 = 白牌引擎 + 许可证
  自动化运营 = 结算引擎 + 监控大盘
```

### P5 🟢 Queen Admin + 结算引擎（1 月）

> **战略意义：** 虫后从手工操作中解放，自动化运营支撑规模化增长。

**为什么在 P5：**
- 初期（<10 合伙人），手工算佣金用 Excel 能顶住
- 当合伙人超过 10 人、客户超过 50 家，手工必崩
- P5 是"从能用到好用"的关键转折

**交付清单：**

| 模块 | 路径 | 交付物 |
|------|------|--------|
| Admin API | `queen/api/ admin/` | 全局大盘 + 合伙人管理 + 客户总览 + 结算引擎 + Overlord 监控 + 内容管理 |
| Admin 前端 | `queen/web/ admin/` | 5 页 SPA |
| 结算引擎 | `queen/api/ admin/ settlement.go` | 自动算佣金（双轨制 × 阶梯）→ 生成账单 → 触发打款 |

**页面规划：**

| 页面 | 功能 | 价值 |
|------|------|------|
| 全局大盘 | GMV / MRR / ARR / 客户增长 / 续费率 / 渠道健康度 | 一眼看全盘 |
| 合伙人管理 | 核心合伙人绩效 + 城市合伙人审批/绩效 | 团队全貌 |
| 客户总览 | 所有企业客户 / 合同状态 / 健康评分 | 客户全貌 |
| 结算管理 | 自动算佣金 → 生成账单 → 审批 → 打款 | 告别 Excel |
| Overlord 监控 | 所有客户 Overlord 实例健康状态 | 挂了马上知道 |

**结算引擎逻辑：**

```
每月 1 日 00:00 自动执行：
  1. 拉取上月所有客户的订阅费 + 星能消耗 + 增值服务费
  2. 按归属关系匹配到核心合伙人 / 城市合伙人
  3. 按双轨制（A轨/B轨）× 阶梯（铜/银/金/钻）计算分成
  4. 城市合伙人场景：额外计算核心合伙人渠道管理服务费
  5. 首年 vs 续费使用不同费率
  6. 生成佣金账单 → 管理员审批 → 触发银行打款

每月 5 日：出上月账单
每月 10 日：完成打款
```

**解锁：**
- ✅ 自动化结算 → 不再手工算佣金
- ✅ 全局监控 → 客户 Overlord 挂了能及时发现
- ✅ 数据驱动决策 → GMV/MRR/ARR/续费率一目了然

```

  用户上传图片/截屏 → Vision 模型理解 → Agent 处理

  场景：营销短视频、产品演示、教学内容

**Phase 10b：主动式 Agent + A2A**

```

  不再等用户提问，主动发现问题并处理
  
  示例：
  - 监控 Agent：每小时检查服务器 → 发现异常 → 自动创建工单 + 通知
  - 销售 Agent：监控 CRM → 客户 30 天未活跃 → 自动发送关怀邮件
  - 财务 Agent：每月 1 日 → 自动生成财报 → 发送给管理层

Agent-to-Agent 协议（A2A）：
  Agent 之间可以互相发现、协商、委托任务
  
  示例：
  - 销售 Agent 发现技术问题 → 委托给技术 Agent → 返回结果
  - 翻译 Agent 需要专业术语 → 调用行业知识 Agent → 获得准确翻译
  
  信用体系：
  - 每次 A2A 调用记录成功/失败
  - 累计信用评分 → 影响推荐排序和价格
```

**Phase 10c：微调管线 + 知识蒸馏**

    → 蒸馏训练小模型（Qwen-7B / DeepSeek-7B）
    → 本地部署 → 降低推理成本 90%+
```

- **P8 和 P9 可部分并行**：可观测性（P8b）和安全加固（P9b）互相独立
- **P10** 依赖全栈就绪：P7 P2P + P8 Agent 经济 + P9 开发者生态 → 才有规模化 AI 原生的土壤

## 五、开发原则

| # | 原则 | 说明 | 适用阶段 |
|:-:|------|------|---------|
| 1 | **先能卖，再能管，再放大** | P0 解锁收入 → P2-P3 解锁渠道 → P4-P5 解锁规模 | P0-P5 |
| 2 | **每步解锁一个商业能力** | 不做"技术很酷但不赚钱"的东西 | 全阶段 |
| 3 | **一个人阶段只做可独立交付的** | P0-P1 是创始人两个月内能干完的 | P0-P1 |
| 4 | **渠道工具：外部 > 内部** | 城市合伙人需要后台建立信任，核心合伙人用微信先顶着 | P2-P3 |
| 5 | **技术护城河放最后** | P2P/进化是终极壁垒，但初期不影响卖货 | P6-P7 |
| 6 | **复用 Claw 能力** | Overlord web 不重写 AI 能力，代理到管辖 Claw 实例 | 全阶段 |
| 7 | **增量交付** | 每个 Phase 结束后都是可用产品，不存在"做了三个月还不能用"的情况 | 全阶段 |
| 8 | **平台思维：让别人替你干活** | Agent 经济 + 插件市场 = 外部创作者创造价值，平台抽成 | P8-P9 |
| 9 | **安全是大单的入场券** | 等保三级/SOC2 不是技术债，是客单价 ¥50K+ 的门票 | P9 |
| 10 | **AI 原生不是功能，是范式** | 多模态/主动式/A2A 不是"加功能"，是重新定义 Agent 交互方式 | P10 |

## 八、收入模型演进

```
P0-P5 阶段（卖产品）：
  收入 = Overlord 订阅 + 星能消耗
  客单价 ¥999-¥9,999/月
  天花板：客户数 × 订阅单价

P8 阶段（经营平台）：
  收入 = 订阅 + 星能 + Agent 交易抽成 + 插件抽成
  创作者发布付费 Agent → 平台抽 20%
  开发者发布付费插件 → 平台抽 20%
  天花板：平台 GMV × 抽成率（理论上限远高于 B2B 订阅）

P10 阶段（AI 原生经济）：
  收入 = 平台抽成 + 数字员工订阅 + A2A 调用计费 + 微调服务
  Agent 互相调用 → 每次计费 → 平台抽成
  企业定制微调 → 服务费 + 持续推理费
  天花板：Agent 网络效应 → 指数增长
```
